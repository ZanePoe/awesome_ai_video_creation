# रैंकिंग विधि और सीमाएँ

GitHub मेट्रिक्स GraphQL API से एक तय UTC क्षण में बैच में लिए जाते हैं। स्नैपशॉट तभी परमाणु रूप से बदला जाता है जब सारे बैच सफल हों। एक ही अपवाद है वह रिपॉज़िटरी जिसे GitHub अब हल नहीं करता (नाम बदला या हटाया गया): उसका पिछला रिकॉर्ड बना रहेगा और `missing_upstream` तथा `missing_since` समय-मुहर के साथ चिह्नित होगा, ताकि एक गायब प्रोजेक्ट दैनिक रिफ्रेश न तोड़े। रेट लिमिट, ट्रांसपोर्ट त्रुटियाँ और आंशिक GraphQL प्रतिक्रियाएँ अभी भी रन रोक देती हैं और पुराना स्नैपशॉट जैसा है वैसा रखती हैं।

- stars: कम्युनिटी ध्यान का सूचक।
- 30/90 दिन की कमिट: डिफ़ॉल्ट-ब्रांच के पूरे इतिहास की गिनती, जिसमें डॉक, मर्ज और बॉट कमिट भी शामिल हैं।
- नवीनतम कमिट: डिफ़ॉल्ट-ब्रांच के HEAD का समय; किसी अन्य ब्रांच का push या रिपॉज़िटरी मेटाडेटा बदलाव को कोड अपडेट नहीं माना जाता।
- release, archive और लाइसेंस पहचान ऑडिट के लिए अलग सहेजी जाती है।

पहले चार लेयर बनाई जाती हैं — पिछले 90 दिनों में कमिट, 91–365 दिन बिना कमिट, 365 से अधिक दिन बिना कमिट, और संग्रहित/ऐतिहासिक — फिर यह गणा जाता है:

```text
P = min(1, ln(1 + stars) / ln(1 + 100000))
A = min(1, ln(1 + commits_90d) / ln(1 + 500))
R = exp(-days_since_default_branch_HEAD / 90)
मेंटेनेंस स्कोर = 100 × (0.40P + 0.35A + 0.25R)
```

मेंटेनेंस स्कोर फ़ाइनल वीडियो की गुणवत्ता, संपादन-सौंदर्य, जनरेटिव मॉडल की क्षमता, गति, VRAM, लागत या कॉपीराइट-सुरक्षा का स्कोर नहीं है। monorepo और बॉट कमिट गतिविधि को बढ़ा-चढ़ा सकते हैं; स्थिर मॉडल रिपॉज़िटरी भी लंबे समय तक कम कमिट कर सकते हैं।

लाइसेंस की स्वचालित पहचान और मैन्युअल समीक्षा अलग रखी जाती हैं। Remotion, Hunyuan, Wav2Lip, Palmier, FFmpeg आदि शर्तयुक्त, मिलित या संस्करण-आधारित लाइसेंस पर चलते हैं; मॉडल वेट, सामग्री, फ़ॉन्ट और थर्ड-पार्टी सेवा की शर्तें अलग हो सकती हैं।

किसी समान क्षमता-परीक्षण में सामग्री, स्क्रिप्ट, मॉडल संस्करण, बजट और हार्डवेयर तय रखने चाहिए, और जनरेशन सफलता दर, शॉट सुसंगतता, उपशीर्षक/लिप-सिंक, टाइमलाइन संपादनीयता, मैनुअल सुधारों की मात्रा, रेंडरिंग समय, VRAM, API लागत और आउटपुट लाइसेंस अलग-अलग दर्ज करने चाहिए।
