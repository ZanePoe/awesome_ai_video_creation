# 2026-11-25 刷新脚本容忍消失的仓库

触发点：`awesome_agent_memory` 的每日 `Refresh GitHub metrics` 因 `FlowElement-xinliuyuansu/m_flow` 返回 404 而整轮失败（`gh: Could not resolve to a Repository with the name ...`）。原设计「任一批次失败即保留上一份完整快照」在有仓库消失时会让 CI 每天红一次。

按用户决定改为两类失败分开处理：

- GitHub 明确解析不到某个仓库（`MISSING` 正则匹配 stderr 里的 `owner/repo`）：把这些仓库从该批次剔除后重试一次，消失的仓库沿用上一份快照记录并加 `missing_upstream: true` 与 `missing_since` 时间戳；`collected_at` 保持原值，说明这行数字来自哪一次采集。若上一份快照里没有该仓库（首次采集就 404），仍报错并要求先从 `data/projects.json` 移除条目——不能凭空造数据。
- 其他失败（限流、传输错误、GraphQL 部分返回、仓库存在但无默认分支）：行为不变，抛错并保留旧快照。

`main()` 读取上一份 `data/metrics.json` 作为 `previous`；文件损坏或不可读时按空处理（原子替换逻辑仍由「先写 .tmp 再 rename」保证，已有测试覆盖）。控制台会打印 `Carried forward N vanished repositories: ...`。

新增测试：`test_vanished_repository_is_carried_forward`（一次失败批次 → 重试剩余仓库 + 消失仓库带标记，`run` 调用两次）与 `test_vanished_repository_without_history_still_fails`（无历史可沿用时必须报错）。`docs/methodology.md` 与四种语言的镜像同步说明该口径。

同批在 `awesome_agent_memory` 处理的两条上游变化见该仓库 `record/2026-11-25-上游仓库消失与更名.md`：`FlowElement-xinliuyuansu/m_flow` 已消失且 org 下 0 个公开仓库，搜索到的 `s16173760/m_flow` 所有者不同，故删除条目（90 → 89）；`unibaseio/membase` 更名为 `membaseai/membase`（证据提交 `59100235` 在新所有者下仍可取到），显示名按官方 README 改为 `Membase`。
